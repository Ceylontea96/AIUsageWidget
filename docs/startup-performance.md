## 병목과 개선 순서

1. **캐시 복원 때 레이아웃 갱신을 묶기.** EXE 캐시 복원 `load_cache()`는 중앙값 252ms였다. 캐시 없는 경우 전체 생성자는 211ms, 캐시 있는 경우 451ms였다. `load_cache → render → relayout → apply_mode` 호출 때문에 시작 중 `relayout`이 1회에서 4회, `apply_mode`가 2회에서 5회로 늘어난다. 캐시 있는 EXE에서 전체 `relayout` 누적 시간은 중앙값 127ms였다. 세 카드의 데이터·렌더링을 반영한 뒤 전체 레이아웃을 한 번 갱신하는 변경을 우선 검증할 만하다. 이 수치 전체가 절감된다는 의미는 아니다.
2. **정상 설치의 실행 준비 경로 단축.** EXE에서 PowerShell 진입까지 309ms, 이후 Python 탐색·검증에 126ms가 들었다. 검증된 Python 경로를 활용하는 빠른 실행 경로와 기존 설치·복구 경로를 검토할 가치가 있다. Python 삭제·업그레이드 시의 복구 동작을 함께 보존해야 한다. Python 직접 실행과의 차이를 그대로 절감 예상치로 사용해서는 안 된다.
3. **import 중 불필요한 초기화 지연.** 위젯 import는 약 200ms였다. 별도 프로파일에서 `providers.py`의 모듈 전역 `urllib.request.build_opener()`가 약 40ms였고, 대부분 기본 인증서 로딩이었다. 실제 HTTP 요청이 필요할 때 초기화하는 후보로 검토할 수 있다. 프로파일 실행은 타이밍 표본과 별개이며 계측 오버헤드가 있다.

이번 프로파일에서 링 PNG 생성은 약 7ms, 번들 폰트 등록은 약 6ms였다. 파일 차단 해제 역시 약 15ms로, 위 세 후보보다 우선순위가 낮다. 합성 캐시는 실제 계정의 복잡한 추가 한도 화면 비용을 대표하지 않는다.

`Start-Sleep -Milliseconds 1200`은 자식 Python 실행 이후의 종료 확인이다. 캐시 있는 EXE에서도 화면 준비보다 중앙값 464ms 늦게 끝났다. 이 대기를 제거하면 런처의 종료는 빨라지지만, 이번 측정의 화면 준비 병목은 해결되지 않는다.

`load_cache`, `relayout`, `apply_mode` 시간은 중첩된다. cProfile의 누적 시간도 호출 트리상 중복되므로 서로 더하지 않는다. 개선 후에는 같은 도구로 다시 측정하고, 캐시 복원·다양한 배율·접힌 카드·추가 한도·창 위치의 동작을 검증해야 한다.

## 후속 개선: 캐시 복원 레이아웃 일괄 갱신

`load_cache()`에서 카드와 축약 표시를 먼저 갱신하고, 복원한 항목이 있으면 마지막에 `relayout()`을 한 번 호출하도록 변경했다. 캐시 복원 이외의 `render()` 호출은 기존처럼 즉시 레이아웃을 갱신한다. 잘못된 캐시는 건너뛰고, 비활성 서비스는 숨김 상태를 유지한다.

캐시 복원에 따른 `relayout` 호출은 3→1회, 창 위치 배치를 포함한 시작 전체에서는 4→2회로 줄었다. 전체 `apply_mode` 호출도 5→3회가 됐다.

전체 테스트 종료 후, EXE/Python 직접 실행 × 변경 전/후 × 각각 5회로 캐시가 있는 경우 20회를 비교했다. 매 쌍의 실행 순서를 번갈아 바꾸었고, 두 패키지는 `usage_widget.py`만 다르다. 인터프리터와 계측 방식은 최초 측정과 같다. 아래 수치는 이전 표와 시간을 두고 얻은 결과이므로 이전 표의 값과 직접 차감하지 않는다.

## 후속 개선: 검증된 Python으로 바로 시작하기

설치 스크립트가 위젯을 정상으로 띄운 뒤, 그때 쓴 Python과 주요 파일의 크기·수정 시각을 `%APPDATA%\AiUsageWidget\runtime-v1.txt`에 기록한다. 다음부터 `AI Usage.exe`와 로그온 VBS(`--startup`)는 이 기록이 모두 맞을 때 PowerShell 없이 `pythonw.exe`를 직접 실행한다.

- 기록 조건: 설치 스크립트가 띄운 그 프로세스가 창을 만들고 `widget.instance`에 자기 PID와 창 핸들을 남겼을 때만 기록한다. 초기화 오류 창만 띄운 채 살아 있는 프로세스는 기록하지 않는다. `pyw.exe` 같은 버전 선택기는 기록하지 않는다.
- 사용 조건: 설치 폴더, `python.exe`·`pythonw.exe`의 경로와 크기·수정 시각, `usage_widget.py`와 `setup_and_run.ps1`의 크기·수정 시각이 모두 같아야 한다. 하나라도 다르거나 기록이 손상됐으면 기록을 지우고 기존 설치 스크립트 경로로 실행한다.
- 실패 복구: 직접 실행한 위젯이 1.2초 안에 0이 아닌 코드로 끝나면 기록을 지우고 설치 스크립트 경로로 한 번 다시 실행한다. 0으로 끝나는 경우(이미 실행 중인 위젯을 앞으로 가져온 경우)는 정상으로 본다.
- PATH: 설치 스크립트처럼 사용자·시스템 PATH를 다시 읽어 넘긴다. 위젯을 켠 뒤 설치한 CLI도 찾을 수 있게 하기 위해서다.
- 별도 파일을 쓰는 이유: `install.json`은 런처와 설치 스크립트가 파일 전체를 두 키로 덮어쓰므로, 새 키를 넣으면 지워진다.
- 로그온 VBS의 `launch.log` 기록: VBS의 텍스트 스트림은 시스템 코드페이지(한국어 Windows는 CP949)로 쓰는데, 날짜를 `Now`로 적어 `오후` 같은 지역화된 한글이 UTF-8 로그에 섞여 있었다. 측정 도구가 이 로그를 UTF-8로 읽다가 실패해서 드러났다. 이제 VBS는 숫자 날짜와 ASCII만 쓰고, 경로의 한글 등은 `\uXXXX`로 적는다.

## 후속 개선: HTTP 연결 준비를 첫 요청으로 미루기

`providers.py`는 import할 때 `urllib.request.build_opener()`로 공용 URL opener를 만들었다. 이 호출이 시스템 인증서 저장소를 읽느라 약 40ms가 걸리는데, 실제 요청은 조회 작업 스레드에서만 한다. 이제 opener는 첫 요청 때 만든다. 여러 조회가 동시에 첫 요청을 보내도 잠금으로 한 번만 만든다.

- import 단독 측정(Python 3.14, 각 10회 이상): `providers` import가 중앙값 약 149ms에서 약 107ms로, `providers` 자체 실행 시간이 46ms에서 16ms로 줄었다.
- 전체 시작 측정: `tools/compare_startup.py --file providers.py --cache populated --samples 5`. 변경 전(`HEAD`)과 변경 후 `providers.py`를 번갈아 20회 실행했다.

| 중앙값 (범위) | 변경 전 | 변경 후 | 감소 |
|---|---:|---:|---:|
| EXE의 import 구간 | 235ms | 202ms | 33ms |
| Python 직접 import 구간 | 245ms | 221ms | 24ms |
| EXE 첫 화면 준비 | 1,480ms (1,468–1,664) | 1,420ms (1,384–1,548) | 60ms |
| Python 직접 첫 화면 준비 | 775ms (747–793) | 773ms (760–997) | 약 0ms |

- import 구간은 10쌍 모두에서 줄었다(쌍별 9–50ms).
- 전체 시간의 차이는 실행마다의 변동(생성자 구간만 해도 ±40ms)보다 작아, 이 표본으로는 전체 시작이 빨라졌다고 단정할 수 없다. 개선 폭은 import 구간 수십 ms로 본다.

원본은 `dist/startup-comparison-20260925-215604/results.json`에 있다. 데이터에 변경 후 `providers.py`의 SHA-256을 기록했다.
